# Project Decisions

| Date | Decision | Reason | Consequence / impact |
| --- | --- | --- | --- |
| 2026-10-01 | QUBO is the common optimization formulation. | It provides the shared formulation for classical and quantum/hybrid directions. | The dashboard's model workflow presents QUBO → Ising → quantum/hybrid optimization. |
| 2026-10-01 | The current classical direction is classical QUBO optimization. | It is the selected non-quantum optimization path for later integration. | The user-facing solver choice is named Classical QUBO. |
| 2026-10-01 | QAOA is the quantum optimization direction. | It is the planned quantum/hybrid approach to the QUBO/Ising formulation. | The UI exposes a Quantum / Hybrid QAOA demo workflow only. |
| 2026-10-01 | MILP is not part of the current user-facing workflow. | The current research prototype is scoped to QUBO and QAOA directions. | No MILP solver option or implementation is present. |
| 2026-10-01 | The dashboard is built incrementally rather than rebuilt. | The project must preserve and extend the existing Flask/vanilla-JS prototype. | Changes should be additive and avoid unnecessary restructuring. |
| 2026-10-01 | User-defined problem instances are a project requirement. | The project needs to support instances beyond the fixed baseline. | A `POST /api/instances` in-memory interface exists; complete custom-builder UI is still pending. |
| 2026-10-01 | EV-to-station travel cost is represented internally as `detour[e][s]`. | A matrix directly expresses per-EV, per-station travel cost. | No maps, GPS, or routing API is required for this feature. |
| 2026-10-01 | The baseline fixture must remain unchanged. | It is the fixed reference for the 3 × 2 × 4 demonstration. | Objective 10.1 and baseline assignments/costs must be preserved. |
| 2026-10-01 | QAOA is evaluated experimentally; quantum advantage is not assumed. | Demo values cannot support performance claims. | Current QAOA metrics are labeled demo or placeholder; no advantage/speedup claim is made. |
| 2026-10-02 | Simulated Annealing (SA) is the primary classical QUBO solver. | It operates directly on the binary QUBO formulation and provides a practical heuristic baseline for comparison with QAOA. | Simulated Annealing is implemented in `evcore.solver_sa`. It exposes iterations, temperatures, cooling schedule, seed, and restarts. It does not require an arbitrary upper bound on objective value; limits are expressed through budgets. Tabu Search and MILP are not primary solvers. |
| 2026-10-02 | Exact Enumeration is implemented separately for small instances only. | Its purpose is solely validating the QUBO formulation, determining exact ground truth optimum for small instances, and calculating optimality gaps for heuristic and quantum solutions. | Implemented in `evcore.exact_solver` for instances with N ≤ 20 variables. All methods evaluate on the exact same QUBO formulation. |
| 2026-10-02 | Optimization pipeline follows: Problem Instance → QUBO Construction → Binary QUBO → SA → Best Binary Solution → Decoder → Feasibility Validation → Objective + Cost Breakdown → Dashboard. | Ensures clear separation of concern, strict domain feasibility checking, and transparent objective/cost accounting. | Standardized payload structure across API and dashboard with bitstring decoding, constraint violation reporting, and cost breakdowns. |
| 2026-10-02 | Binary variable count on the Model page is dynamically derived from active instance dimensions. | Hardcoding 22 variables was misleading for custom instances (e.g. 2×2×2 instance has 6 variables). | Variable count updates dynamically in UI ($N = n_{st} + \sum_e n_{st} \times \|W_e\|$). |
| 2026-10-02 | Physical Grid Performance analytics are decoupled from objective grid-stress penalties. | Physical grid capacity violations and utilization metrics evaluate decoded schedules, while quadratic stress remains part of the optimization objective. | Result view reports Peak Load, Peak Utilization, Average Utilization, Near-Capacity Slots, and Capacity Violations without conflating them with objective stress penalties. |
| 2026-10-02 | EV charging schedule table uses semantic HTML table (`table.schedule-table`) instead of fixed CSS grid columns. | Fixed CSS grid template columns (`repeat(4, 1fr)`) caused cells to wrap and misalign EV rows as headers whenever $N_t \neq 4$. | Dynamic HTML table correctly aligns arbitrary $(N_{ev}, N_t)$ dimensions with strictly EV rows and time-slot columns. |
| 2026-10-05 | Bounded custom problem limits are enforced at max 8 EVs, 5 stations, 8 time slots. | Problem-definition limits must prevent out-of-control memory consumption while allowing realistic small-to-medium research instances. | Enforced in frontend input elements, JavaScript validation, and backend API (`POST /api/instances` returns 400). Problem can have up to 325 QUBO variables. |
| 2026-10-05 | Qiskit Aer QAOA simulation limit is strictly capped at 24 logical qubits. | Statevector simulation memory grows exponentially ($2^N$). Simulating above 24 qubits locally risks browser/server memory exhaustion. | Clear separation between problem limits (up to 325 vars) and QAOA simulation limit (24 qubits). If $N > 24$, QAOA returns clean `unsupported_size` status without executing large statevectors or fabricating results. SA continues to solve. |
| 2026-10-05 | Quantum QAOA evaluates on the exact same QUBO formulation and decodes via the exact same decoder. | Aligns with the core thesis story: Same Problem $\to$ Same QUBO $\to$ SA / QAOA $\to$ Same Decoder $\to$ Same Validation $\to$ Comparison. | No separate or simplified QUBO formulation is used for QAOA. Both candidate bitstrings are validated against physical constraints identically. |
| 2026-10-05 | Measured quantum circuit resources are derived from genuine Qiskit circuit analysis. | Rigorous scientific honesty requires reporting real circuit characteristics rather than heuristic estimates. | Measures circuit depth, transpiled depth (basic basis gates `['u', 'cx']`), two-qubit gates, total gates, variational parameters ($2p$), and shot counts. |
| 2026-10-05 | Comparative metrics and load charts are displayed conditionally only when multiple solvers are executed. | Running a single solver (SA-only or QAOA-only) should focus on that solver's result and schedule without showing empty comparison blocks. | Comparison table and dual-bar load charts render only when multiple solvers are selected/run. |
